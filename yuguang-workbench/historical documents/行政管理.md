#### 1. 项目背景

镇安文投公司行政管理工作目前以「一份 SOP 工作清单 + 一批制度 Word 文档 + 飞书审批 + 分散在各部门的纸质/电子件」的方式运行。清单把行政工作拆成 7 大模块 24 个事项，并明确了每个事项应有的制度、模板、OA 审批、第三方平台与台账要求；但**要求与执行之间缺少载体**：

- 制度只有名字，模板大多没有实体文件；
- 台账靠人工汇总，14 处「自动汇总/自动归档」停留在愿望层面；
- 上千份合同以双章扫描件形式散在业务部、项目部手中，无统一台账，无法回答「合同在谁手上、什么时候到期」；
- 领导要的指标（证照到期、合同到期、归档及时率）无从统计。

本应用的目标不是再造一个 OA，而是**把 SOP 的 24 条「要求」翻译成可执行、可留痕、可统计的系统规则**，并与已有的飞书能力（免登录、云空间、审批）对接，避免重复建设。

**本项目明确不做**：不做独立 Web 系统、不自研低代码平台、不重建审批流、不接管人事异动流程。

#### 4. 技术方案

##### 4.1 总体形态

**飞书自建应用**，嵌于飞书工作台，移动端优先（H5）。不做独立 Web、不用多维表轻方案。

##### 4.2 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue 3 + Vant 4 + Pinia | 包体小，飞书容器兼容稳定 |
| 后端 | NestJS 10 + TypeORM | 模块化清晰，匹配引擎/业务分层 |
| 数据库 | PostgreSQL 15 | JSONB + GIN 索引支撑通用记录检索 |
| 任务 | `integration_task` 表驱动（一期不引 MQ） | 单机足够，运维简单 |
| 部署 | 阿里云 ECS 2C4G + Nginx + Docker | 一期单机；每日备份 + 合同双备份 |
| 大模型 | DeepSeek（二期，OCR 增强用） | 一期不依赖，`R-OCR-1` 风险不阻塞 |

##### 4.3 实现路线：方案 A（配置驱动，收敛版）

- 用 JSON Schema 描述每张单的字段，前端渲染、后端校验落库；
- 台账视图与归档规则统一；
- **三条红线**：不做表单设计器、不做页面设计器、不做流程设计器；
- 字段类型白名单 10 种：`text / textarea / number / date / select / multiselect / user / dept / file / table`；
- 特殊逻辑白名单 3 项：**库存计算、会议冲突检测、运单号反查**——可写代码，不进引擎。

##### 4.4 架构分层

```
apps/web  (Vue3 + Vant)          H5 前端
apps/api  (NestJS)
  modules/auth          飞书免登、角色解析
  modules/engine        schema、通用记录 CRUD、归档、空月
  modules/contract      合同主数据、轻台账导入、用印关联、状态机
  modules/asset         资产/耗材、库存、盘点
  modules/meeting       会议室与冲突检测
  modules/express       快递与运单反查
  modules/integration   通讯录/云空间/审批/消息/事件
  modules/kpi           指标与预警
  modules/audit         操作留痕
```

#### 5. 遗留问题（历史短板）

1. **制度与模板只有名字、没有实体**：12 个模板、5 个制度、3 个操作指引，均无正文/文件，无法直接驱动系统表单设计。
2. **「自动化」全是口号、没有机制**：表格 14 处提到「自动汇总/自动归档」，但没有定义：触发时机（审批通过？月末？）、归档命名规则、落盘位置、失败重试、人工补录入口。这是最容易在实施阶段返工的地方。
3. **多平台职责边界不清**：飞书（审批/多维表/日历/云文档）、与光工作中台、顺丰/联通/享像派/国家企业信用信息公示系统，四类数据源谁做主数据、谁做副本，未定义；「同步」是单向还是双向也未定义。
4. **台账「按月归档」缺少判定与兜底**：多次出现「当月没有可不出报告、不归档」，但谁判定、怎么判定、空月是否留痕，无规则。
5. **资产口径模糊**：「资产与设备管理」与「办公用品与后勤物资管理」边界（固定资产 vs 低值易耗）未定义，直接影响资产台账与折旧。
6. **角色权限只有要求、没有矩阵**：飞书组织架构同步免登录虽有方案，但「24 个事项分别谁能看/谁能提交/谁能审/谁能归档」从未固化成矩阵。
7. **缺管理指标**：表格全是「留痕」要求，没有一条「管理者要看什么数」（证照到期预警、印章使用频次、资产盘点差异率、费用预算执行率等）。
8. **模块七被明确排除**（仅提醒、不建流程），需求范围必须与此对齐，否则会无边界膨胀。

#### 2.2 流程状态机（推导）

**审批通过 ≠ 已盖章 ≠ 已归档。** 合同与用印至少需要四态：

`申请 → 审批通过 → 已盖章 → 已归档`

- 「盖章」是行政的**执行动作**，不是审批动作（制度第四/六条：保管人核对单文一致后盖章）。
- 「归档」是**第三个动作**，SOP 要求按月归档并标注日期。
- 台账只有在「已盖章」后才应计入用印次数；只有「已归档」后才算完成闭环。

## 4. 阶段 3 · 方案比较

> 源文件：`.project-board/stages/03-solution-comparison.md`　|　9,807 字节　|　204 行　|　S-1~S-4 四个分歧点的对比与裁定

### 阶段 3 · 方案比较

- 开始：2026-10-19 17:48
- 承接：阶段 2 需求清单（[02-requirements.md](02-requirements.md)，25 事项 + 合同线 16 条）
- 目标：把「怎么做」摆成可比较的选项，逐项给出成本、风险与推荐，由负责人裁定

---

#### 0. 本阶段目标与完成标准

**目标**：对三个真正的架构分歧点给出至少 2 个可行方案，量化对比优劣，形成可裁定的结论。

**完成标准**

1. 每个分歧点给出 ≥2 个方案，含成本粗估、风险、适用条件。
2. 明确「推荐哪个」及理由，且理由可被反驳（不是拍脑袋）。
3. 负责人对每个分歧点做出选择，记入 `state.json` 的 `decisions_log`。
4. 未决项登记为待确认，不带入设计阶段。
5. 经负责人确认后进入阶段 4 设计确认。

**本阶段不做的事**：不画界面、不建表结构、不写代码。

---

#### 1. 三个真正的分歧点

需求澄清已经把「做什么」钉死，剩下的分歧只有三处：

| 编号 | 分歧点 | 影响面 | 状态 |
|---|---|---|---|
| S-1 | 实现路线：配置驱动 vs 逐项硬编码 vs 低代码/多维表 | 全部 25 事项的工期与后期维护 | ✅ 已定为 A |
| S-2 | 合同线是否在一期给一个轻量版本 | 一期工期 +3~5 人天 vs 合同风险敞口 | **待裁定** |
| S-3 | 存量合同迁移路径：全量 OCR / 分期 / 轻台账 | 二期 60~80 小时人工 + 流水线开发 | **待裁定** |

---

#### 2. 决策点 S-1：实现路线

##### 方案 A：配置驱动的表单引擎（收敛版）

- 用 JSON Schema 描述一张单的字段，前端按 schema 渲染，后端按 schema 校验与落库
- 台账视图统一（列表 + 筛选 + 导出），归档规则统一（按月 + 命名模板 + 云空间目录）
- **只抽象「单 → 台账 → 归档」三件套**，不做表单设计器、不做页面设计器、不做流程设计器
- 库存计算、会议冲突检测、运单号反查三项单独写代码

| 维度 | 评估 |
|---|---|
| 一期工期 | 引擎 5 人天 + 11 项 × 0.5 ≈ **10.5 人天** |
| 二期工期 | 25 项 × 0.5 ≈ **12.5 人天** |
| 维护成本 | 改字段 = 改配置，不发布版本 |
| 特殊逻辑适配 | 需要预留「自定义钩子」，否则库存类需求会被迫 hack |
| 主要风险 | 过度抽象，滑向自研低代码平台 |

##### 方案 B：逐项硬编码

- 每个事项一套页面 + 一张表 + 一套归档逻辑

| 维度 | 评估 |
|---|---|
| 一期工期 | 11 项 × 1.5 ≈ **16.5 人天** |
| 二期工期 | 25 项 × 1.5 ≈ **37.5 人天** |
| 维护成本 | 改字段 = 改代码 + 发版 |
| 特殊逻辑适配 | 天然适配，没有抽象成本 |
| 主要风险 | 二期维护成本爆炸，字段变更频繁时团队会被拖住 |

##### 方案 C：飞书多维表 + 自动化 / 现成低代码平台

| 维度 | 评估 |
|---|---|
| 一期工期 | **最快，约 3~5 人天** |
| 能力上限 | 撑不住合同多对多、库存计算、权限隔离、OCR 抽取 |
| 结论 | **不可行**（与 D-13 已排除的形态一致） |

##### 对比结论

| | A 配置驱动 | B 硬编码 | C 低代码/多维表 |
|---|---|---|---|
| 一期 | 10.5 | 16.5 | 3~5 |
| 二期 | 12.5 | 37.5 | 不可行 |
| 三期 | 1.5 | 4.5 | — |
| **合计** | **≈24.5** | **≈58.5** | — |
| 边际成本 | 递减（0.5/项） | 恒定（1.5/项） | — |

**推荐 A，且已由负责人于 17:50 裁定选择 A。**

**A 的三条红线**（写进设计约束，防止滑向低代码平台）：

1. 不做表单设计器——表单由开发按 schema 手写配置，业务方不自由拖拽。
2. 不做页面设计器——页面布局固定几种模板。
3. 不做流程设计器——审批流仍在飞书审批里配，本应用只消费。

#### 3. 决策点 S-2：合同线是否进一期

背景：一期定为 P1（后勤/会务/文化/快递），合同线在二期。但合同线在需求澄清中投入了 6 轮问答，且存量迁移周期最长。

##### 选项 1：纯二期

- 一期不含任何合同能力
- 优点：一期最纯粹，工期最短
- 缺点：上千份合同在二期才「有身份」，期间仍是散在各部门的 PDF

##### 选项 2：一期给合同轻量版（推荐）

- 范围：合同登记（编号/名称/类别/甲乙方/金额/签订日/到期日/经办人）+ PDF 挂接 + 用印关联 + 实物存放位置
- **不含**：OCR 自动抽取、到期自动预警、变更续签、交叉查询
- 成本：约 **3~5 人天**（复用方案 A 的引擎，主要是批量挂接与列表）
- 收益：一期结束就有「合同在哪、谁手上、有没有盖章」的底账；二期只做字段补录与预警
- 风险：一期范围从 11 项变 12 项，工期 +3~5 天

##### 选项 3：一期给轻量版 + 手填到期日即可预警

- 在选项 2 基础上，允许人工填到期日，填了就能出预警（不依赖 OCR）
- 成本 +1 人天
- 收益：租赁、服务类合同能提前看到风险，不必等二期 OCR

| 维度 | 选项 1 | 选项 2 | 选项 3 |
|---|---|---|---|
| 一期工期增量 | 0 | +3~5 人天 | +4~6 人天 |
| 合同风险敞口 | 全敞口到二期 | 底账建立，字段可后补 | 底账 + 到期预警 |
| 是否依赖 OCR | — | 否 | 否（手填） |
| 推荐 | | **推荐** | 推荐（若你更怕合同逾期） |

#### 4. 决策点 S-3：存量合同迁移路径

| 路径 | 做法 | 粗估代价（1,000 份） | 适用条件 |
|---|---|---|---|
| 全量 OCR | 全量 OCR → 抽取 → 40% 人工复核 | 流水线 3~5 人天 + 复核 60~80 小时 | 合同是核心资产，必须全字段可查 |

#### 1. 数据模型

##### 1.1 设计原则

1. **一套通用记录表 + 少量专用表**。通用表承载 11 个「单-台账-归档」类单元；合同、资产、库存、会议室预订四类有特殊逻辑，用专用表。
2. **所有记录带公共字段**：`id / unit_code / dept_id / owner_id / created_by / created_at / month_key / status / archive_state`。
3. **业务字段放 JSONB**，但**检索与统计用到的字段抽出为独立列**（如金额、到期日、资产编号）。
4. **删除一律软删**（`deleted_at`），台账不允许物理删除——这是审计要求。

##### 1.2 实体清单

| # | 表 | 类型 | 说明 |
|---|---|---|---|
| 1 | `sys_user` | 通用 | 飞书用户映射：open_id、union_id、姓名、部门、角色 |
| 2 | `sys_dept` | 通用 | 部门树（来自飞书通讯录） |
| 3 | `sys_role` | 通用 | 6 个角色 + 数据范围（self / dept / all） |
| 4 | `form_schema` | 引擎 | 每个单元的字段定义（JSON Schema）、校验规则、必填项 |
| 5 | `biz_record` | 引擎 | 通用台账记录（11 个单元共用），`data` 为 JSONB |
| 6 | `biz_file` | 引擎 | 附件：file_token、关联对象、类型、上传人 |
| 7 | `archive_batch` | 引擎 | 归档批次：月份、单元、状态（待确认/已归档）、确认人 |

##### 1.3 关键设计

**（1）通用记录表 `biz_record`**

```sql
id            uuid pk
unit_code     text      -- 单元：hygiene / supplies / safety / maintenance / express / reception / meeting / outreach / activity / welfare / material
dept_id       text      -- 归属部门（权限过滤依据）
owner_id      text      -- 记录责任人
data          jsonb     -- 业务字段（由 form_schema 定义）
month_key     char(7)   -- 2026-10，归档与空月判定依据
status        text      -- draft / submitted / approved / done
archive_state text      -- none / pending_confirm / archived / empty_month
created_by / created_at / updated_at / deleted_at
```

**（2）合同状态机（四态，D-06 推导）**

```
草档(imported/created) → 待用印 → 已盖章 → 已归档
                              ↘ 退回
```

- 「草档」允许不完整（仅文件名 + 类别 + 位置），这是轻台账的落点（D-23）。
- 「已盖章」只能由行政专员的盖章确认动作触发，不能由审批通过自动进入（D-06）。
- 「已归档」需人工确认批次（D-17 B 档）。

**（3）合同 ↔ 用印 多对多**

`contract_seal_link(contract_id, seal_event_id, note)` —— 一份合同可挂多次用印，一次用印可挂多份合同（D-10）。

**（4）资产与耗材的判定（D-19）**

```
if 单价 >= 1000 and 使用年限 >= 1  → asset
else if 需维修/报废管理             → asset_change 的例外清单
else                               → inventory_item
```

判定在采购审批入账时执行一次，结果字段 `asset_or_consumable` 固定，不随后续改价变动。

**（5）「空值≠无风险」（D-23 约束）**

合同表中 `amount`、`expire_date` 允许为 NULL，但必须同时写 `data_completeness` 字段（`full / partial / minimal`），列表与预警页对 `minimal` 显示「未补录」标记，**预警只对 `full` 生效，`partial/minimal` 进「待补录」队列而非「无风险」**。

##### 1.4 表单配置（方案 A 的核心）

```json
{
  "unit_code": "safety",
  "name": "安全巡检记录",
  "fields": [
    {"key": "inspect_date", "label": "巡检日期", "type": "date", "required": true, "index": true},
    {"key": "area", "label": "巡检区域", "type": "select", "options": ["办公区","仓库","机房"], "required": true},
    {"key": "items", "label": "巡检项", "type": "table", "columns": [...]},
    {"key": "issue", "label": "存在问题", "type": "textarea"},
    {"key": "fix_due", "label": "整改期限", "type": "date", "required": false}
  ],
  "ledger": {"columns": ["inspect_date","area","inspector","issue","fix_due"], "sort": "inspect_date desc"},

```

字段类型白名单（不做设计器，只支持这几种）：`text / textarea / number / date / select / multiselect / user / dept / file / table`。

#### 3. 接口清单（外部）

| # | 接口 | 调用时机 | 输入 | 失败兜底 |
|---|---|---|---|---|
| I-1 | 飞书免登换 token | 每次打开应用 | JSAPI authCode | 失败提示重进；缓存 2h，静默续期 |
| I-2 | 通讯录-部门/用户 | 每日 02:00 全量 + 异动事件增量 | dept_id | 失败保留上次快照，告警 |

| 部署单点 | 单机故障即全站不可用 | 一期接受；每日备份 + 合同数据双备份 |
| 飞书接口限流 | 批量拉审批可能触发限流 | 增量拉取 + 5 分钟窗口 + 指数退避 |
