# 与光工作中台 Git 协作规范

## 角色

- Codex 是默认实现者，负责业务逻辑、权限、数据模型、接口和部署变更。
- Harness 默认只读审查；只有 Codex 明确交接后，Harness 才能接手同一任务的写入。
- 同一任务同一时间只有一个写入者。审查者不得修改实现者的 worktree。

## 分支和 worktree

- `main` 只接受已验证、可发布的变更。
- 每项工作使用 `task/<编号>-<短名>` 分支。
- 每个任务使用独立 worktree；禁止在主工作目录直接开发。
- worktree 目录统一放在仓库内的 `.worktrees/`，该目录必须被 Git 忽略。

## 交接

交接记录必须包含目标、已改文件、当前测试结果、未解决问题、下一步和提交号。接手者先检查 `git status`、分支和测试，再开始修改。

## 范围

与光承载公司级行政、人事、财务、法务、项目和经营管理能力。跨应用数据只能通过已批准的接口合同交换，不直接读取其他应用数据库。

## 合并门槛

必须通过类型检查、相关测试、敏感信息扫描和人工差异审查。任何凭据、真实业务数据或平台导出包不得提交。

## 进度与上下文纪律

- 每次回复末尾报告：`阶段：<名称> | CTX：statusline / 未检测 | 建议：继续 / 收尾 / 切换对话`。不得虚构上下文百分比。
- 任务完成并通过审查、用户要求继续/恢复/交接、或发现上下文可能丢失时，更新 `.project-board/state.json`、`board.md` 和 `events.jsonl`。
- statusline 超过 70% 时，不开始新任务；先收尾并更新进度板，再建议切换对话。
- 进度板缺失时，依据 Git 状态和可验证记录恢复，不猜测任务状态。
