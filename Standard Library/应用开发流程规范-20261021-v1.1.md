# 应用开发流程规范

- **版本**：v1.1（2026-10-21）
- **状态**：发布候选稿（待负责人签发）
- **适用范围**：与光工作中台、工具层、大项目应用、经营实体应用及其接入应用
- **替代关系**：本稿签发后，替代《应用开发流程规范-20261020-v1.0》；签发前以既有已批准规范为准。
- **定位**：规定应用从需求澄清、Demo、实现、验证到部署的阶段顺序。组织、任务、通知、权限、接口和文件归档规则仍以对应的已批准业务规范为准。
- **核心路线**：Codex 完成需求与设计、实施计划、基础可操作 Demo 及优先本地验证；Demo 达到交接门槛后，将完整交接包交给用户指定的顶级模型完成正式实现；之后先本地回归，再按用户决定进入测试环境和生产部署。

## 一、适用规范和冲突处理

本规范与以下文件配套执行：

1. 《组织架构管理规范》
2. 《应用搭建结构规范》
3. 《网盘映射管理与文件命名规范》
4. 《任务发布与管理规范》
5. 《统一信息通知与应用消息通道规范》
6. 《任务接口合同》
7. 《与光任务功能配置启动清单》
8. 《五份规范一致性自检记录》

业务规则以对应已批准的业务规范为准；开发阶段顺序和交接要求以本规范为准。发生冲突、缺项或无法按环境验证时，记录问题、影响范围和建议方案，等待负责人决策；不得自行改写正式业务规则。用户明确的当前指令优先于本流程中的默认安排，但不能据此绕过数据、权限、安全和生产接入门槛。

## 二、Superpowers 工作链

Superpowers 是一组流程技能，不应误称为产品固定定义的“十个阶段”。每个应用按需求选择并执行相关技能；项目可以把工作细分成约十个跟踪步骤，但不得为了凑数跳过、伪造或重复流程。

Codex 应在当前环境和项目允许范围内完成适用的工作链，通常包括：

1. 读取项目现状、规范、Git 状态和进度板。
2. 澄清需求与约束，区分已确认事实、决策、假设和待确认问题。
3. 形成设计/spec，完成自审并按项目要求取得设计确认。
4. 编写可执行的实施计划，明确文件范围、任务、测试和验收证据。
5. 使用隔离工作区或项目规定的安全分支工作方式。
6. 按适用要求执行测试先行、逐步实现和阶段性验证。
7. 对实现进行代码评审、缺陷修复和回归。
8. 执行完成前验证，记录真实命令、结果和未验证边界。
9. 完成 Demo 及其测试记录，整理可供其他模型接手的交接包。

如果某项技能因项目规模、代码库状态或环境限制不适用，记录原因和替代验证方式。不得声称完成了未执行的流程或测试。

## 三、阶段与退出门槛

### 阶段0：恢复项目事实与确认规范

- 阅读当前项目的 AGENTS.md、适用标准、`.project-board/state.json`、`board.md`、`events.jsonl`、handoff（如存在）、Git 状态和相关近期提交。
- 核实当前代码、运行方式、部署方式和环境依赖；历史材料只作证据，不自动作为现行需求。
- 确认 application_id、应用/模块负责人、租户归属、授权映射和适用接口合同；未知项不得臆造。

**出口**：当前事实、规范版本、已知未知项和工作区风险均有记录。

### 阶段1：需求澄清与设计

- 明确目标用户、业务目标、核心流程、角色权限、数据范围、外部依赖和验收条件。
- 对重大未决业务规则逐项提问；一次聚焦一个关键问题，不以沉默当作批准。
- 输出设计/spec，覆盖模块边界、数据流、权限、菜单（不超过四级）、错误处理、第三方依赖、可替换边界和验收场景。
- 按项目流程审阅设计；未确认的业务规则保持待定，不进入依赖该规则的实现。

**出口**：设计及其边界清楚，关键决策有依据，用户要求的设计确认已完成。

### 阶段2：实施计划与开发准备

- 输出可以由零上下文工程师执行的实施计划：文件清单、细分任务、实际测试命令、预期结果、回退点和交接产物。
- 建立隔离工作区并保护现有未提交更改；遵守仓库自己的分支、worktree 和提交规则。
- 确认本地运行时、依赖、测试数据和环境变量模板；密钥不得写入仓库或日志。
- 对工作台接口、机器人、云盘等外部依赖，优先准备本地替身/模拟器和可用的沙箱配置；生产凭证和生产副作用不得用于本地测试。

**出口**：计划可执行，开发和本地验证环境具备；外部依赖中尚未可用的部分已标为模拟或待联调。

### 阶段3：Codex 实现基础可操作 Demo

- 由 Codex 按已确认设计和计划开发基础可操作 Demo，优先保证核心流程真实可操作，不以静态页面或截图充当 Demo。
- Demo 可使用明确标记的假数据、模拟 API 或本地持久化；模拟边界必须显眼记录，不得声称已连通生产系统。
- 至少实现核心页面和状态流转、关键输入校验、正常/空/错误状态、权限边界的可验证表现，以及对应验收步骤。
- 开发应保持模块职责清晰；身份、通知、任务、文件、模型或第三方服务通过明确边界/适配器隔离，避免难以替换的厂商耦合。
- 每个独立改动按计划运行相关测试；对关键逻辑使用有意义的自动化测试。需要修复失败时先定位原因，不得通过跳过测试来制造通过结果。

**出口**：Demo 能在本地启动并完成约定的核心流程；启动命令、限制、变更文件和自测证据已记录。

### 阶段4：优先线下验证和 Demo 评审

默认先在本地开发机或本地隔离测试环境验证，**不得把线上部署作为当前阶段的完成条件，也不得催促用户进行线上部署**。

至少验证：

- 本地全新启动步骤和关键用户流程；
- 业务规则、权限边界、输入校验、错误/空状态和状态流转；
- 数据持久化、重复操作、并发修改或冲突（适用于该功能时）；
- 单元/集成/API/端到端测试中与风险匹配的部分；
- 本地依赖不可用、第三方超时/失败时的预期行为；
- Demo 与真实系统间的差异、尚未验证的安全和性能事项。

所有 P0/P1 缺陷必须修复并复测。线上测试、云端压力测试或生产部署不是 Demo 通过的必要条件；若本地环境不能验证某项，准确标记为“未验证”，给出后续环境条件和测试方法，不可虚构通过。

**出口**：Demo 评审通过，问题清单、测试输出、截图/录屏（如有）、模拟边界和未验证项归档。此出口只表示 Demo 可用于确认需求，不表示正式系统或生产环境已验收。

### 阶段5：交接顶级模型完成正式实现

Demo 评审通过后，按用户指定的模型和工具链交给顶级模型（可为 Codex、Claude Code 或其他模型）实现正式版本。模型不是规范来源，不能自行推断或修改已确认业务规则。

交接包必须包括：

- 最新已批准业务规范及其版本，不以摘要替代原文；
- 用户确认的需求/spec、决策记录、待定事项和实现计划；
- Demo 的代码位置/提交、运行命令、测试记录和模拟边界；
- 验收清单、已知风险、未验证事项、目标环境约束和禁止事项；
- 当前 Git 状态、修改范围、迁移/回滚注意事项和交接后的首要任务。

执行模型必须先读仓库指令和交接包，再按实施计划逐项完成正式实现。可以在同一次模型交接中承担整项开发，但必须分任务验证、保留测试证据并完成代码审查；“一次性交付”不等于一次生成全部代码后跳过检查。若模型或模型厂商发生变化，接口和业务规则保持不变，重新核验输出格式、工具调用、依赖版本、测试结果和安全边界。

遇到规范冲突、关键信息缺失、计划与代码现状不符或无法安全执行时，停止受影响部分并报告具体问题；不得擅自扩展范围。模型改动后必须保留可审查的文件差异和提交/版本信息。

**出口**：正式实现完成，计划任务有状态，测试/评审结果和差异清单可复核；未完成事项显式列出。

### 阶段6：正式实现本地回归

在更新任何线上环境前，先使用与正式实现对应的代码完成本地构建、测试和核心流程回归。至少检查：

- 格式、静态检查、类型检查、单元及集成测试（按项目提供）；
- 核心用户流程和权限矩阵；
- API/数据迁移兼容性、重复请求和失败恢复；
- 日志、密钥处理、审计和敏感数据保护；
- 依赖清单、配置样例、启动说明和本地部署可复现性；
- 高风险接口的并发、超时、限流和资源使用验证计划。压力目标必须来自已确认的用户量/SLO；没有目标时标为待确认，不编造容量保证。

**出口**：本地回归通过，或未通过项已归类并退回修复；对云端真实行为保持明确的验证边界。

### 阶段7：测试环境部署与联调（按需）

- 仅当本地回归通过、环境和账号已准备、且联调确有必要时，再部署到测试/预发布环境。
- 先验证兼容性和外部接口沙箱；按接口合同验签、幂等、去重、重试、补偿、权限和租户路由。
- 执行与实际风险相匹配的并发、压力、恢复和备份还原验证；不得将 Demo 测试或本地模拟表述为云端压力测试。
- 每个测试环境变更记录版本、配置来源、迁移结果、日志和回滚步骤。禁止在无用户授权时操作生产服务、真实数据或生产通知。

**出口**：测试环境联调证据完整，缺陷关闭或有负责人和阻断结论。

### 阶段8：生产发布准备与部署（仅按用户明确要求）

线上部署不是默认下一步，不得以“规范要求”为由催促用户部署。只有用户明确提出上线/部署后，才按当前部署规范准备发布。

生产发布前应具备：负责人批准、版本和变更清单、目标环境确认、配置/密钥安全检查、备份及恢复方案、数据库迁移和回滚方案、健康检查、监控告警、容量假设、发布/停机窗口、验证步骤和回退触发条件。任务和通知类生产接入仍必须满足各业务规范中的全部门槛，特别是机器人、来源应用通知板块、具体办理深链、权限复核和接口联调。

任何生产部署、真实通知开关、数据迁移或会产生外部影响的操作都必须有用户明确授权。未授权时只交付可审查的发布计划，不执行。

**出口**：经授权部署后完成发布后检查并记录实际结果；未部署时如实报告“未部署”，不能标记上线完成。

## 三、云端可用性与质量要求

即使优先线下测试，正式实现仍须为未来云端使用留出可验证方案：

1. 记录运行时/数据库/缓存/队列/存储依赖和版本范围；配置与密钥分离。
2. 页面、业务逻辑、数据访问和外部服务边界清晰；AI/模型、消息、文件和身份等厂商集成经适配器隔离，便于替换。
3. 关键业务写操作具备权限检查、输入校验、事务或幂等保护；有审计日志且不泄露凭证或敏感正文。
4. 说明健康/就绪检查、日志、错误处理、备份恢复和水平扩展时的共享状态要求。
5. 对长任务和外部调用考虑超时、限流、重试、退避、熔断和失败补偿，避免无限重试与重复副作用。
6. 对并发容量、性能目标、用户规模和数据保留期，只依据用户确认或实测证据；未知项列为风险，不做无依据承诺。
7. Demo 中的前端模拟、内存数据和本地存储不能冒充正式后端、持久化、权限或多用户并发实现。

## 四、通知、组织、任务和文件业务边界

以下既有规则持续适用，本规范不作修改：

- 组织架构和统一员工 ID 使用已批准的唯一来源；双租户身份保留租户来源、登录入口和对应飞书 user_id。
- 跨应用数据仅通过与光工作中台批准的接口交换，禁止直接读取其他应用数据库。
- 各应用负责本应用业务页面、业务状态和办理流程；与光总通知中心负责汇总、统计和审计，不代替来源应用办理业务。
- 任务类型固定为日常任务、经营任务、项目任务；支持向下发布和同级协作，不支持向上发布或下属辐射；协作字段选填；发布人负责验收，驳回须写原因。
- 业务通知由来源应用对应租户的自有机器人发送；深链回到来源应用并重新校验权限；发送失败时应用内通知保留并可重试/补偿。
- 附件和正式文件按已批准的网盘映射规范归档；不将文件放入未批准的对象存储。
- 菜单最多四级；不复制业务办理页面到与光工作台。

具体字段、接口路径、状态定义、文件夹和命名规则以对应最新批准文件为准。

## 五、缺陷、回退与交接纪律

- 缺陷按影响分级；权限越权、租户串流、数据丢失、重复业务副作用和密钥泄露属于上线阻断问题。
- 失败时先定位原因，保留复现步骤和证据，修复后重跑受影响测试及必要回归。
- 设计或需求变化回到阶段1更新决策/spec/计划；实现缺陷回到阶段3或阶段5修复；部署失败按发布回滚方案处理。
- 每个阶段完成、暂停、交接或恢复时，按项目要求更新 `.project-board/state.json`、`board.md`、`events.jsonl` 和 handoff；写后必须重新读取并校验。
- 交接须包含目标、已完成工作、变更文件、Git 状态/提交、测试输出、未验证事项、阻塞问题和下一步。
- 不报告虚构的测试、部署、压力或生产验证结果；没有真实 CTX statusline 时报告“未检测”。
