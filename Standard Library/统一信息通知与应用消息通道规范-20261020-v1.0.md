# 统一信息通知与应用消息通道规范

- **版本**：v1.0（2026-10-20）
- **状态**：正式版
- **适用范围**：与光工作中台、工具层、大项目应用和经营实体应用的应用内通知、业务事件通知及飞书机器人消息
- **配套文件**：《任务发布与管理规范-20261020正式版》《任务接口合同-20261020正式版》《五份规范一致性自检记录-20261020》

## 一、定位与核心原则

统一信息通知能力由与光工作中台统一治理，但业务通知由来源应用负责投递和办理。与光工作中台提供统一通知中心、权限过滤、去重、状态汇总、逾期统计、租户路由和审计；来源应用提供本应用通知板块、具体业务页面和本应用飞书机器人。

核心原则是：**统一汇总、应用投递、原应用办理**。

1. 所有接入应用产生的任务、轻审批、工作流节点、系统待办和异常事件，进入与光统一通知中心汇总。
2. 来源应用必须在本应用内提供统一的信息通知板块，展示本应用相关通知。
3. 业务通知由来源应用自己的飞书机器人发送给对应租户的本人；与光工作台自身产生的通知由与光工作台机器人发送。
4. 员工点击通知后必须打开来源应用的具体办理页面或该应用内对应通知详情，不统一跳转到与光工作中台办理。
5. 与光总通知板块用于跨应用查看、未读汇总、逾期总览和统计分析；它是汇总入口，不替代来源应用办理入口。

## 二、与五份规范的衔接

1. **组织架构**：通知接收人使用与光统一组织架构的员工 ID，并通过租户来源、登录入口和飞书 `user_id` 路由到本人账号。通知不建立第二套人员目录。
2. **应用架构**：通知按五层应用架构记录 `application_id`。工具层、大项目应用、经营实体应用和工作台均可成为通知来源；来源应用负责业务页面和机器人。
3. **网盘**：通知附件只保存文件 ID、网盘链接和权限索引，正式文件继续遵守网盘映射与命名规范；通知中心不建设独立文件存储。
4. **任务管理**：任务事件进入统一通知中心，但任务通知的飞书消息由任务所属应用机器人发送；任务状态和验收仍按任务规范处理。
5. **租户边界**：同一自然人在多个租户有账号时，按来源应用所属租户选择对应账号和机器人；不因通知汇总而合并租户数据。

## 三、通知来源范围

### 3.1 任务通知

包括任务发布、接收确认、修改、提交反馈、验收通过、驳回、取消、逾期和自动转派。任务所属应用是通知来源应用。

### 3.2 轻审批通知

包括轻审批发起、待审批、审批通过、审批驳回、撤回和补充材料。审批页面和正式执行留在产生该轻审批的应用；如审批实际在飞书 OA 完成，来源应用应提供回到对应 OA 或应用业务页面的深链。

### 3.3 工作流节点通知

包括节点到达、节点处理、节点转交、节点退回、节点完成、异常和超时。通知必须标注当前节点和下一步动作。

### 3.4 系统和业务异常

包括同步失败、权限变更、数据冲突、附件处理失败、接口失败和需要人工处理的异常。敏感内容不直接写入机器人消息，消息只显示摘要和处理入口。

## 四、统一通知中心

### 4.1 工作台总通知板块

与光工作中台提供统一通知板块，至少包括：全部通知、未读通知、待办理、已完成、逾期通知、按应用筛选、按通知类型筛选、按时间筛选和关键词搜索。

总通知板块显示跨应用汇总信息和逾期总览，展示来源应用、来源模块、标题、摘要、状态、创建时间、截止时间、优先级和“打开来源应用”操作。点击业务通知必须跳转来源应用，不在总通知板块内复制业务办理流程。

### 4.2 应用内通知板块

每个接入应用统一提供信息通知板块，至少包括：未读、待办理、已处理、逾期和全部通知。应用内通知详情应显示来源事件、业务摘要、当前状态、操作记录和进入具体办理页面的按钮。

应用可根据自身菜单采用 2 级模块或既有通知模块承载，但必须遵守四级菜单规则，不新增第五级菜单。

## 五、通知消息和深链字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `notification_id` | 是 | 工作台生成的全局通知 ID |
| `source_application_id` | 是 | 来源应用 ID |
| `source_module_id` | 否 | 来源模块 ID |
| `source_event_id` | 是 | 来源应用事件 ID，用于幂等 |
| `tenant_id` | 是 | 消息投递所属租户 |
| `target_employee_id` | 是 | 工作台统一员工 ID |
| `target_feishu_user_id` | 是 | 对应租户的飞书账号 ID |
| `notification_type` | 是 | 任务、轻审批、工作流、系统或异常 |
| `title` | 是 | 简短标题 |
| `summary` | 是 | 不含不必要敏感信息的摘要 |
| `status` | 是 | 未读、已读、待办理、已处理、已逾期、已失效 |
| `priority` | 是 | 高、中、低 |
| `due_at` | 否 | 办理截止时间 |
| `deep_link` | 是 | 来源应用具体办理页面或应用通知详情页 |
| `action_label` | 是 | 例如“去办理”“查看结果” |
| `created_at` | 是 | 创建时间 |

深链必须经过来源应用登录态和权限校验。员工没有权限或业务已失效时，来源应用显示清晰的无权访问或已关闭提示，不把业务处理转移到与光工作台。

## 六、应用机器人和租户路由

### 6.1 机器人归属

每个已上架飞书的应用使用自己的飞书机器人。机器人属于该应用在对应租户的企业自建应用配置，不共享其他应用的机器人身份。

### 6.2 路由规则

1. 先根据 `source_application_id` 确定来源应用。
2. 再根据应用承载租户确定 `tenant_id`。
3. 再根据统一员工 ID 获取该租户下经过人工核验的 `target_feishu_user_id`。
4. 使用来源应用在该租户的机器人发送消息。
5. 同一员工在多个租户有账号时，按来源应用租户分别投递，不跨租户转发。

与光工作台机器人只发送工作台自身通知、统一系统通知和无法归属具体应用的中台异常，不代替来源应用发送业务消息。

### 6.3 消息内容

机器人消息至少包含来源应用名称、通知标题、摘要、优先级、截止时间（如有）、当前状态和来源应用深链。消息不包含访问令牌、完整敏感附件内容或不必要的跨租户信息。

## 七、通知生命周期和可靠性

1. 来源应用提交事件后，工作台校验应用、租户、员工和可见范围，生成通知记录。
2. 工作台按 `source_application_id + source_event_id + target_employee_id` 幂等，不重复生成通知。
3. 通知先写入统一中心，再异步向来源应用投递通知事件；来源应用写入本应用通知板块并调用自己的机器人发送，应用内通知不能因机器人失败而丢失。
4. 机器人发送失败时按退避策略重试，超过次数进入失败队列并通知应用负责人；应用内通知保留失败状态。
5. 应用必须支持按 `notification_id` 补偿查询和重复事件安全处理。
6. 已读、待办理、已处理和逾期状态由来源应用回传或由工作台根据约定事件更新；总通知和应用通知状态最终一致。

## 八、权限、安全和审计

通知可见范围沿用来源业务的组织、应用、模块、项目和实体授权。统一通知中心不得因为汇总而扩大可见范围。

机器人消息只投递给目标本人或来源业务明确授权的人员。通知详情和深链打开时重新执行来源应用权限校验。离职、账号失效或租户绑定撤销后，停止新消息投递；历史通知按业务留痕规则保留。

工作台和来源应用分别记录通知创建、权限判定、去重、发送、重试、已读、打开、办理、失败和人工补偿日志。日志不得记录机器人凭证、访问令牌或附件原文。

## 九、统计和逾期总览

与光工作中台统一汇总通知数量、未读数、待办理数、已处理数、逾期数、机器人发送成功率、失败率、平均处理时长和按应用分布。逾期总览只展示用户有权查看的通知，不改变来源应用的业务状态和办理责任。

来源应用可以展示本应用统计，但统计口径和通知 ID 以统一中心为准。

## 十、接口要求

来源应用至少实现：

- 通知事件提交接口；
- 通知查询和详情接口；
- 已读、待办理、已处理状态回传接口；
- 具体业务深链；
- 机器人租户配置和发送结果回调；
- 失败事件补偿查询接口。

建议采用以下接口路径，具体版本由工作台接口注册表统一管理：

| 接口 | 方向 | 用途 |
| --- | --- | --- |
| `POST /api/notification/v1/events` | 应用 → 工作台 | 提交业务通知事件 |
| `GET /api/notification/v1/notifications` | 应用 → 工作台 | 查询本应用有权查看的通知 |
| `GET /api/notification/v1/notifications/{notification_id}` | 应用 → 工作台 | 获取通知详情和深链元数据 |
| `POST /api/notification/v1/notifications/{notification_id}/read` | 应用 → 工作台 | 回传已读 |
| `POST /api/notification/v1/notifications/{notification_id}/status` | 应用 → 工作台 | 回传待办理、已处理等状态 |
| `POST /api/notification/v1/delivery-results` | 应用 → 工作台 | 回传本应用机器人发送结果 |
| `GET /api/notification/v1/compensation` | 应用 → 工作台 | 查询失败或漏收事件 |

工作台向来源应用发送 `notification.created`、`notification.updated` 和 `notification.expired` 事件。来源应用收到事件后写入本应用通知板块，并使用本应用在对应租户的机器人发送消息；工作台不代替应用使用业务机器人的凭证。所有接口均要求请求签名、幂等键和应用身份校验。

统一事件结构：

```json
{
  "source_application_id": "app_xxx",
  "source_module_id": "module_xxx",
  "source_event_id": "event_xxx",
  "tenant_id": "tenant_xxx",
  "target_employee_id": "emp_xxx",
  "target_feishu_user_id": "ou_xxx",
  "notification_type": "task",
  "title": "任务待办理",
  "summary": "请完成本周库存盘点",
  "priority": "high",
  "due_at": "2026-10-21T18:00:00+08:00",
  "deep_link": "https://source-app.example/tasks/tsk_xxx",
  "action_label": "去办理"
}
```

## 十一、菜单层级映射

与光工作中台：

```text
工作台（1级）
└── 信息通知（2级）
    ├── 全部通知（3级）
    ├── 待办理（3级）
    ├── 逾期通知（3级）
    └── 通知统计（3级）
```

各应用：

```text
应用业务大类（1级）
└── 信息通知（2级，或纳入既有通知模块）
    ├── 未读通知（3级）
    ├── 待办理（3级）
    └── 全部通知（3级）
```

## 十二、验收标准

1. 各接入应用均有统一信息通知板块。
2. 任务、轻审批、工作流节点和异常事件可进入统一通知中心。
3. 与光工作台可查看跨应用未读、待办和逾期总览。
4. 来源应用使用自己的对应租户飞书机器人发送消息。
5. 员工点击机器人消息后直接打开来源应用具体办理页面。
6. 与光工作台不代替来源应用办理业务。
7. 多租户员工按来源应用租户和本人飞书账号准确投递。
8. 通知事件幂等、失败可重试、可补偿，应用内通知不因机器人失败丢失。
9. 通知权限不扩大业务权限，深链打开时重新校验权限。
10. 未读、待办理、已处理、逾期和发送失败状态可追踪并审计。

## 十三、发布与实施

本规范作为第五份正式规范发布。各应用上架飞书并完成机器人配置后，必须按本规范提供通知板块、事件接口、租户账号映射、深链和发送回执；与光工作中台负责统一通知中心、汇总、路由、统计、审计和失败补偿。未完成深链和租户机器人联调的应用不得开启生产通知。
