# 五份规范一致性自检记录

- **日期**：2026-10-20
- **范围**：组织架构、应用搭建结构、网盘映射与文件命名、任务发布与管理、统一信息通知与应用消息通道
- **结果**：通过；发现的表述差异已在任务和通知规范中通过交叉引用收敛

## 一、边界检查

| 检查项 | 结果 | 结论 |
| --- | --- | --- |
| 组织来源 | 通过 | 通知接收人和任务接收人均使用统一工作台员工 ID，不建立第二套人员目录 |
| 双租户身份 | 通过 | 按来源应用租户和对应飞书 user_id 投递，不因汇总合并租户数据 |
| 应用分层 | 通过 | 来源应用保留业务页面、状态和办理责任；工作台做汇总、路由、统计和审计 |
| 任务同步 | 通过 | 任务总看板和应用看板同步，通知按任务所属应用机器人投递 |
| 轻审批与工作流 | 通过 | 事件进入统一通知中心，正式办理留在来源应用或约定的飞书 OA 页面 |
| 网盘文件 | 通过 | 通知和任务只保存文件索引与权限信息，正式文件仍按网盘映射归档 |
| 权限 | 通过 | 汇总不扩大业务可见范围，深链打开重新校验来源应用权限 |
| 菜单 | 通过 | 统一通知、任务看板均遵守四级规则，不新增第五级 |

## 二、入口和消息路径检查

```text
来源应用事件
  → 与光统一通知中心汇总、去重、统计、逾期总览
  → 来源应用自己的租户机器人发送
  → 员工点击
  → 来源应用具体办理页
```

与光工作台自身事件使用与光工作台机器人；与光总通知只承担汇总查看和跳转，不复制业务办理。

## 三、任务规范专项检查

- 任务通知不改变任务状态机，验收、驳回、取消和逾期仍由任务规范负责。
- 任务通知不重新定义任务权限，继续使用应用、模块、组织和项目/实体授权。
- 任务附件仍使用任务所属应用的网盘映射路径。
- 任务应用内看板只显示本应用任务，但应用通知板块可显示本应用的任务、轻审批、工作流和异常通知。

## 四、已知实施前提

1. 各应用必须提供稳定的具体办理深链，并在打开时执行自身权限校验。
2. 各租户、各应用必须分别配置企业自建应用机器人，不得共用机器人凭证。
3. 工作台必须维护员工 ID、租户来源和租户飞书 user_id 的核验绑定。
4. 各应用必须实现事件幂等、失败回执和补偿查询。
5. 通知汇总、机器人发送和来源应用办理需要分别验收，不能以机器人发送成功代替业务办理成功。

## 五、结论

五份规范之间没有发现组织主数据、租户边界、应用归属、网盘归档、任务闭环或通知入口冲突。最终统一为：**与光统一汇总，来源应用投递，来源应用办理**。

前三份规范的标题和状态已按已发布口径统一为正式版，五份规范现在具有一致的发布状态标识。
