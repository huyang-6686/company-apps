## 3. 页面数据共享关系（历史推断）

建议把以下对象作为协会内部统一主数据候选：

- `member`：会员单位和会员联系人；
- `employee`：协会内部人员；
- `organization`：组织和部门；
- `project`：项目及负责人；
- `fee_record`：会费应收、实收、减免和票据；
- `financial_entry`：收支和凭证；
- `archive_record`：档案、文件和归档状态；
- `approval_instance`：外部审批实例及同步状态。

潜在共享关系：

1. 会员是会费、项目参与、品牌展示和档案材料的关联主数据。
2. 项目是预算、支出、负责人和归档材料的关联主数据。
3. 会费收款进入财务汇总，但必须避免会费模块和收支模块双重记账。
4. 外部审批实例关联员工、组织、项目、财务或档案对象，并保留来源系统 ID。
5. 迎检材料应引用业务记录和档案，不复制出第二份不可追溯数据。

以上为数据关系设计候选，不是当前应用已经实现的证明。

## 4. 与光工作中台技术复盘

### 4.1 登录和身份

- 脱敏源码包含 `auth` 模块、认证 Guard、登录控制器和 Bearer Token 处理。
- 存在传统账号密码认证。
- 存在飞书授权码登录入口。
- 员工与系统用户存在关联，历史材料显示使用手机号关联；统一不可变身份键是否存在，待确认。

### 4.2 角色和权限

- 有角色装饰器和角色校验。
- 有页面权限装饰器和页面权限 Guard。
- 有权限服务和权限控制器。
- 历史资料提及角色、页面权限和部门数据范围。
- 数据权限是否仅由应用层控制，还是已启用 PostgreSQL RLS，资料之间存在差异，待以运行环境核验。

### 4.3 OA、组织和附件同步

- 有飞书认证、通讯录/组织同步、审批、附件、通知、考勤和云盘相关服务。
- 历史复盘称部分 OA 同步偏手动。
- 与光项目规划提出事件订阅实时推送 + 定时任务补偿，并以租户和审批实例 ID 幂等。
- 协会不应直接依赖与光字段；应建立统一领域模型和来源适配器。

## 5. 望向山经营中台技术复盘

- 源码包观察到 React/TypeScript 前端、NestJS 服务端、Drizzle ORM、PostgreSQL 和飞书 SDK。
- 有独立的认证、飞书、飞书网盘、设置和 API 模块。
- RBAC 使用角色码和模块权限矩阵，权限档位为 `none/view/edit/manage`。
- 组织人员数据带同步来源标记。
- 前端 API 按业务模块拆分，后端按 NestJS 模块拆分。
- 这些结构可作为协会工程组织参考；业务页面和角色矩阵不能直接复制。

## 7. 同步架构与未来钉钉接入

协会应采用：

```text
协会统一领域模型
  ├── 与光工作中台适配器
  └── 钉钉适配器（预留）
```

字段映射、身份映射、组织映射和审批映射独立于来源系统。未来钉钉接入点至少包括组织架构、通讯录和审批流，并支持双源校验、灰度切换、冲突处理和回滚。

当前与光同步范围建议从登录身份、组织通讯录、角色权限、入职/转正审批和附件开始；未来钉钉范围可扩展到组织架构、通讯录、审批流和消息通知。

主要风险：身份键不一致、组织层级差异、审批字段不兼容、附件权限变化、双源重复事件和切换期间数据冲突。
