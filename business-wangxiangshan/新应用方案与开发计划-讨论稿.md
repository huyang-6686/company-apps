# 望向山新应用实施计划（讨论稿）

> **实施约束：** 仅在业务方案获确认后拆分并执行；当前阶段计划是阶段级讨论稿，不授权开始编码。实施时每个任务都需关联具体文件、测试命令和验收结果。

**目标：** 为望向山咖啡厅建立一个独立、受权限保护、可审计的经营应用，首期聚焦一个现场验证过的业务闭环。  
**架构建议：** 前端、受认证的业务 API 和专属数据存储分层；部署平台与身份集成先做技术验证。应用本地保存门店流程数据，将来只通过受控合同向与光经营中枢上报必要汇总。  
**技术栈候选：** 若采用独立代码应用，评估 React/TypeScript、NestJS、PostgreSQL；若妙搭能力更合适，评估平台原生方案。最终选型须经平台验证。

---

> 状态：待业务讨论，不是已批准需求，不授权开始编码或部署。  
> 目的：基于现有源码、资料和可访问的旧应用页面，重新确定独立新应用的首期范围。  
> 边界：望向山负责咖啡厅自己的业务流程与记录；与光经营中枢负责公司层面的经营汇总。新应用不与其他独立经营应用合并。

## 1. 结论摘要

旧应用可作为业务词汇、历史记录形态和问题案例的参考，不能作为新应用的功能清单、数据模型或代码底座直接继承。它覆盖了成本、采购、人员成本、盘点、产品、收入、日清、报表、营销、生态、档案、学习、AI、飞书与中枢接入等多个领域，但实际运行页面显示这些领域的记录和流程完整度不均。

建议新应用从一个可现场验证的小闭环开始。首期候选优先讨论“每日经营数据录入与核对”，原因是旧运行页面已有收入台账数据，但首页经营汇总、收入分项和日清排班之间出现不一致或缺口。这个候选不是既定需求；须先确认咖啡厅当前的实际录入来源、责任人、核对步骤和指标定义。

首期暂不做与光经营中枢正式同步。新应用先独立保存门店业务记录，并提供内部可审计的查询或导出。只有数据来源、口径、同步频率、权限和失败补偿经双方确认后，才进入中枢接口设计。

## 3. 旧应用复盘

### 3.1 有价值的经验

- 门店经营记录需要从录入、审核、汇总到归档形成闭环，不能只堆菜单和台账。
- 页面应显示数据来源、期间、口径、状态与责任角色；无数据时给出真实空态，不以虚构示例填充。
- 业务主数据应有明确唯一来源。旧资料提出产品/SOP 单一维护、核算标准独立维护等原则，这些原则可讨论继承，但具体边界要由实际流程确认。
- 飞书可以承担身份、组织、网盘等平台能力，但新应用仍要明确应用内授权规则、失败表现和数据访问审计。
- 中枢只需要公司层面确认过的汇总数据，不应默认接收门店所有业务明细。

### 3.2 已观察到的主要问题

1. **汇总不可靠或不可解释。** 收入台账有数据，首页概况却显示无数据；收入记录的合计与渠道分项也不一致。新系统需要唯一计算入口、明确字段定义和可复算的汇总规则。
2. **工作流断点。** 日清页面没有当天排班和任务；管理报表也没有对应任务。没有录入、提交、复核、退回、重开等可理解的状态流转。
3. **记录质量不足。** 抽样费用记录有缺日期、经办人、供应商或待确认归属的情况；采购记录样例有数量、单价与金额需要核验的情况；人员成本记录存在待审核数据。新应用应定义必要字段、校验、异常队列和修正留痕。
4. **功能承诺与实现不一致。** 旧 README 将统一票据入口描述为资产、采购、费用的唯一来源；在线页面/源码仍提示收入导入解析和部分导出功能未完成。新需求要逐条列出可用、部分可用、未实现、暂不做，而不是按旧说明照抄。
5. **权限和文档失配。** 六角色、八角色以及三角色设想同时存在；在线页面也观察到身份显示差异。新系统必须先明确角色、授权来源、后端校验和测试矩阵，再开放业务页面。
6. **集成过早且合同不清。** 旧系统同时存在长连接、回调、HTTP 上报、拉取及轮询实现痕迹，在线连接配置为空。新系统应先完成门店本地闭环，再按正式合同建设单一受控的数据交换机制。
7. **范围膨胀。** 旧应用把日常经营、公司档案、学习、营销、活动、AI、网盘和中枢任务集中在一处。新应用按门店核心业务优先，其他需求逐项确认，不沿用“旧导航里有所以首期也要有”的推理。

### 3.3 历史设计材料中尚待确认的规则

备份内的 `source/AGENTS.md` 记录了若干历史设计决定，但它们不是新应用需求，明天应逐项确认或明确废弃：

- 旧方案排除收银点单、供应链和考勤人事，称这些由外部系统承担；需确认这些系统目前是否仍在使用、是否需要数据导入或仅人工录入。
- 旧方案称设计由绘事署交付、培训由与光工作中台负责，本应用只归档设计成品并只读展示 SOP；需确认现在的系统责任边界和内容所有者。
- 旧核算规则提出物料 A/B/C 三档、主材按日常采购最高价核算、损耗按正常/责任/营销赠送分类、产品毛利率 70% 红线。这些计算会影响经营判断，未核实前不得编码为默认规则。
- 旧方案提出身份由飞书平台管理，并列过三角色 owner/admin/staff；这与其他资料中的六角色、八角色说法冲突。
- 旧 README 对“是否复用飞书已有能力”的表述与同一文档中复用 IAM、网盘、组织能力的方向不一致，应以明天确认的能力清单为准。

### 3.4 本轮没有验证的事项

本次没有做飞书登录流程、不同账号/角色切换、所有页面逐项测试、接口自动化、数据库直连、导入文件处理、AI 识别准确性、飞书长连接状态或中枢联调。在线页面检查属于只读抽样，不能替代验收和数据审计。

## 4. 新应用目标与边界

### 目标

- 支持咖啡厅实际人员完成经确认的首期日常业务闭环。
- 业务记录来源、口径、状态、修改人和时间可追溯。
- 登录与权限保持开启；未授权用户不能通过直接调用接口绕过页面限制。
- 新应用的数据与其他独立经营应用隔离；不复制不必要的个人或明细数据。
- 为将来按批准口径向与光经营中枢汇总数据留出接口边界，但首期不启用正式同步。

### 首期非目标

以下不是当前已批准范围：点单/POS、会员/客户管理、库存自动扣减、供应链、考勤排班、工资核算、完整财务核算、全量档案迁移、AI 票据识别、飞书 OA/网盘自动化、中枢双向通信，以及将其他应用并入望向山。若业务确认其中一项是当前主要痛点，应作为范围决策另行评估。

## 5. 首期候选方案

| 候选 | 内容 | 优点 | 主要风险 | 当前意见 |
|---|---|---|---|---|
| A. 每日经营数据与日结核对 | 按营业日记录已确认的收入/销量指标，补充核对状态、责任人和修订记录；从同一数据源生成日/周汇总 | 与咖啡厅日常管理相关；旧应用已有收入数据，但暴露汇总与日清断裂，便于现场验证 | 指标来源和渠道口径未确认；如果加入排班、POS、多渠道自动导入会迅速扩大 | **推荐作为首期讨论候选**，先限定手工/文件来源并确认字段，不预设 POS 接入 |
| B. 费用/采购记录闭环 | 录入或导入单据，记录分类、金额、供应商、凭证、审核状态 | 旧应用存在大量采购和费用记录，能解决明显的数据清理与归属问题 | 票据识别、分类标准、付款/报销、供应商去重和审批规则复杂，容易变成财务系统 | 如当前首要痛点是费用可信度，可替代 A；建议第一版不含 AI |
| C. 产品/SOP 只读目录 | 维护产品信息与操作资料，供店内查看 | 可将产品和资料口径收敛，适合手机查看 | 历史设计称培训归上级工作中台，产品 SOP 维护权也需确认；对经营记录问题帮助有限 | 暂列后续候选，确认内容所有者后再决定 |

推荐 A 的前提是咖啡厅确认日结/收入核对为真实高频工作。如果确认后 B 更优先，应替换首期模块，不把 A、B、C 一起塞进首期。

优先级是讨论建议，不是最终承诺。

| 优先级 | 功能 | 说明与确认点 |
|---|---|---|
| P0 | 飞书登录/退出与会话识别 | 采用平台认可的 IAM/SSO；不存应用密码；确定单租户/多租户和身份标识 |
| P0 | 应用权限校验 | 确认最终角色；页面和后端接口同时校验；未授权、过期会话和未知角色默认拒绝 |
| P0 | 单一首期业务流程 | 从实际工作中选 A 或 B 或其他一个流程，定义录入、提交、审核、退回、修订和归档状态 |
| P0 | 最小数据模型与审计 | 保存必要业务字段、来源、操作者、时间、状态与更正记录；不建客户/员工敏感明细除非业务确需 |
| P0 | 按同一口径汇总 | 汇总从已确认记录计算，明确时区、营业日边界、舍入、撤销和重开规则 |
| P0 | 空态、错误和异常队列 | 说明无数据、缺字段、重复、超期、审核失败、服务不可用等情况，并可定位责任人 |
| P1 | 可控导入/导出 | 先选定实际文件模板、字段映射、重复识别与错误报告；首期可只做人工录入或单一受控模板 |
| P1 | 简单经营概况 | 仅展示已确认首期模块可复算的指标，并可回到来源记录；不复制一套独立统计 |
| P1 | 飞书网盘凭证/文件链接 | 只有业务确实需要凭证归档时纳入；文件权限、保留策略和本地是否留副本须确认 |
| P2 | 与光经营中枢汇总接口 | 业务口径、字段、方向、频率、访问控制、幂等、失败补偿和审计均定稿后单独开发 |
| P2 | AI 识别、排班同步、营销、档案等 | 按真实使用价值逐项评审，不因旧应用存在而自动列入路线图 |

## 7. 推荐首期流程草案：每日经营数据与核对

该流程只是讨论底稿。确认业务前不锁定字段和角色。

1. **选定数据来源。** 确认当前营业额/杯数/订单数由何种凭据或系统产生、谁保管，以及是否允许人工录入或表格导入。首期不预设 POS 或外卖平台接口。
2. **记录一份营业日汇总。** 以营业日为单位录入最少必要指标和来源说明。旧页面出现过堂食、外卖、其他收入、总杯数、天气、经办人等字段，但新系统只保留经业务确认的字段。
3. **校验和提交。** 校验金额分项与总额、日期、必填字段和重复营业日；发现不一致时给出明确错误，不能静默覆盖或伪造缺失分项。
4. **复核与更正。** 明确谁可以确认、退回或重新打开；每次更正留存操作者、时间、原因和前后值。更正后的汇总可复算。
5. **查看日/周汇总。** 指标可追溯到来源记录；首页和台账共用相同查询口径，不独立维护重复统计。
6. **现场验证。** 至少由实际录入者和实际复核者用脱敏或专门测试记录走完一次正常、缺字段、重复、金额不平和修订流程，再决定扩展。

首期验收标准建议：一名普通用户不能查看或更改无权业务；一条记录可完整提交、复核、退回和修订；汇总与测试凭据逐项一致；重复和不平记录会被拦截或显著提示；所有更正可审计；刷新/重新登录后记录仍一致；测试环境验证备份和恢复流程。具体业务数值与流程待确认后写成验收用例。

## 8. 角色、登录与权限设计

- 身份认证优先使用飞书平台 IAM/SSO 或部署平台正式支持的认证集成，不自建密码登录，不因开发方便关闭认证。
- 认证解决“是谁”，授权解决“可做什么”。授权由服务端执行；仅隐藏菜单不构成访问控制。
- 角色集合尚未确认。历史资料分别出现六角色、八角色以及 owner/admin/staff 三类设想；均不直接继承。明天先确定角色职责，再决定是否按功能权限、数据范围或二者组合授权。
- 明确一个人能否有多个角色、角色从何处赋予、离职/撤权生效时限、系统管理员与业务审核人是否分离。
- 用角色矩阵覆盖读取、创建、提交、审核、退回、更正、导出和配置；敏感人员成本、个人身份信息及经营明细分别讨论最小权限。
- 测试至少包含：未登录、已登录无角色、每个角色、双角色、被撤权账号、直接调用受限 API、跨日/跨范围访问。

## 9. 数据与中枢边界

### 望向山本地数据

由新应用保存首期工作流的业务原始记录、状态和必要审计信息。身份密码不入库；飞书文件可只存经过授权的文件引用和业务元数据。只保存完成业务所需的最少字段，并定义保留、删除、更正和导出规则。

### 未来上报与光经营中枢

默认只讨论经确认的日/月汇总指标，不复制订单、客户、员工明细、票据影像或所有门店配置。接口合同至少明确：

- 指标名称、公式、来源记录、营业日和时区边界、退款/更正如何处理；
- 推送方向、触发时机/频率、是否需要人工批准；
- 每条汇总的稳定业务键、幂等、版本/更正语义和对账方式；
- 认证主体、最小权限、传输加密、密钥轮换、审计与访问范围；
- 超时、重试退避、重复、部分失败、人工重放和告警责任人；
- 中枢确认回执、对账差异处理和数据保留期限。

首期不开放公网匿名接口，不把内部接口直接暴露到公网。若未来采用服务间 API，应通过受控网络/网关、强认证、限流和审计，并单独完成安全评审。

## 10. 技术方案选项

| 方案 | 组成 | 优点 | 代价/风险 |
|---|---|---|---|
| A. 独立代码应用（推荐候选） | Web 前端、受认证的 API、独立 PostgreSQL、部署平台 IAM/SSO 适配 | 数据和发布边界清楚；测试、迁移和后续汇总接口可控 | 需先验证妙搭/目标平台对服务端、数据库、登录和长任务的支持；不能直接照搬旧应用配置 |
| B. 妙搭原生低代码应用 | 平台页面、平台身份、平台托管数据与自动化 | 平台 IAM/数据库能力可复用，部署运维较轻 | 业务规则复杂、审计/迁移/测试能力可能受平台约束；须验证实际接口和导出能力 |
| C. 通用 SaaS/表格先行 | 飞书表格/多维表格等承载极小流程 | 验证业务最快 | 权限、复杂状态机、审计和数据边界可能不足；不宜未经评估成为长期数据库 |

推荐先做技术可行性验证，再锁定平台。若采用独立代码应用，可评估 TypeScript + React 前端、NestJS API、PostgreSQL；旧代码中的依赖、平台 SDK、数据库 schema 和身份实现均需重新审核，不默认复制。开发、测试、生产环境隔离；数据库迁移可回滚；密钥放在部署平台 secret store，缺少生产必需密钥时应用拒绝启动，源码和资料包不保存默认密钥。

## 11. 分阶段开发路线

以下阶段有明确决策门。前一阶段未验收，不把下一阶段视为自动批准。

| 阶段 | 工作内容 | 交付物 | 验收/进入下一阶段条件 |
|---|---|---|---|
| 0. 业务确认 | 访谈录入者、复核者与经营负责人；选一个首期候选；画出现状和目标流程；确认指标与权限 | 业务流程图、字段字典、角色权限矩阵、问题与决策记录、首期验收案例 | 业务负责人确认首期流程和不做事项 |
| 1. 技术可行性 | 验证目标平台登录/SSO、服务端授权、数据库、部署、日志、备份恢复及测试环境；对比方案 A/B/C | 技术决策记录、环境拓扑、风险与成本估算 | 在测试环境完成登录、受限 API、数据库读写、部署回滚的最小验证 |
| 2. 应用底座 | 建立独立代码/环境、认证与授权基础、配置/审计、迁移和测试骨架；不接中枢 | 可部署的空应用、权限验证、审计和备份恢复说明 | 权限负向测试通过；生产配置缺失会失败关闭；可回滚发布 |
| 3. 单模块试点 | 实现已确认的一个业务闭环；统一校验、状态、修订和同源汇总；必要时做单一受控导入 | 可供咖啡厅试用的试点模块、用户说明、验收记录 | 真实角色完成正常与异常用例；记录与凭据/来源一致；关键缺陷关闭 |
| 4. 现场试用与稳定 | 在咖啡厅限定范围试用，收集问题，修正字段与流程；观察实际完成率和错误类型 | 试用报告、变更记录、是否扩围决定 | 业务方确认流程能稳定完成；数据质量达到事先约定标准 |
| 5. 扩展第二模块 | 根据试点反馈重新排优先级，一次增加一个有明确所有者的模块 | 新模块需求与独立实施计划 | 每个模块单独确认范围、权限、数据和验收 |
| 6. 中枢汇总（未来可选） | 双方确认数据合同后实现出站汇总、回执、失败补偿、审计和对账 | 接口契约、权限评审、联调与回滚方案 | 中枢与望向山双方验收同一组脱敏汇总数据及故障恢复 |

粗略估算：在平台和首期业务确认、测试环境可用、无需复杂外部接口的前提下，阶段 0–3 约需 2–4 周单工程师工作量；阶段 4 受咖啡厅现场试用周期影响；阶段 5–6 不纳入首期估时。平台身份或数据接入不可用、需迁移历史数据或新增审批/AI 时需重新估算。

## 12. 测试、部署与变更记录

- **测试分层：** 指标/金额规则单元测试；API 与数据库集成测试；权限矩阵负向测试；关键用户流程端到端测试；浏览器页面抽查；业务方现场验收。
- **数据测试：** 用合成数据覆盖空态、正常值、缺字段、重复、跨营业日、金额不平、退回、修订和并发编辑；测试数据与真实经营数据隔离。
- **部署：** 开发、测试、生产分开；生产部署前执行 schema 迁移检查、备份、健康检查和回滚演练；所有 API 使用 TLS 与认证，内部管理入口不公开。
- **可观测性：** 记录请求追踪 ID、业务操作审计、同步结果和脱敏错误；禁止记录凭证、完整票据内容或不必要的个人数据。
- **变更记录：** 每次需求决策、数据口径调整、权限改动、迁移和发布均记录日期、原因、影响、验证结果和责任人；保留可回滚版本。
- **备份卫生：** 对所有导入/导出包扫描明文密钥、Cookie、个人/客户数据；仅在指定安全位置保留必要脱敏资料。

## 13. 明天需要讨论并决定的问题

### 业务目标

1. 望向山新应用首先要消除的一个具体痛点是什么？高频工作、数据可信、管理透明、减少重复录入，哪一项最优先？

3. 当前真实操作是谁做、何时做、用什么原始凭据、谁复核、出错后如何更正？

### 首期数据

4. 营业日如何界定？收入、渠道、杯数/订单数、退款/折扣等哪些指标真实存在且必须记录？
5. 数据来自人工、现有收银系统报表、外卖平台、表格还是其他来源？首期允许什么录入方式？
6. 哪些字段必须填写，哪些可为空？金额分项与总额如何校验？是否需要附件，附件由谁可见？
7. 历史数据是否迁移？如果要迁，迁哪些期间和字段、由谁核验；如果无必要，是否只从上线日开始记录？

### 角色与权限

8. 最终角色名称和职责是什么？用户此前提到的 8 角色分别是谁、是否为本店实际岗位？
9. 谁可以录入、复核、改已确认记录、导出和配置系统？财务/人员成本等敏感数据的访问边界如何定？
10. 飞书租户、应用可见范围、离职撤权和一个人多角色的处理规则是什么？

### 平台与中枢

11. 新应用仍部署妙搭，还是评估独立托管应用？谁负责平台、数据库和生产发布？

13. 是否需要飞书网盘、审批、AI 或其他现有应用能力？逐项说明业务所有者与必要性，不默认启用。

### 试点与验收
